    xWalk Git cheat sheet¶

    Purpose¶

    This page contains the normal Git commands for the multi-repository xWalk workspace. Run commands from the repository indicated by each section.

    Gerrit is the development and review system. GitHub is a submitted-code mirror. Never push a developer commit, pending patch set, integration pointer, branch, or tag directly to GitHub.

    The workspace has two Git layers:

    • MyPiCarX is the xWalkPiCarAI superproject. It records exact component commits as Git submodule metadata, also called gitlinks.
    • devloper-note, xWalk-rpi5-iw, xWalk-rpi5-tool, and the component directories below xWalk-rpi5-hw are independent repositories.

    Commit a source change in its owning component repository. Do not include a pending component commit in the superproject. After the component change is submitted, the automatic integration uplift creates the reviewed superproject gitlink update.

    Enter the workspace¶

    cd /repo/joxjoh24/MyGitCode/MyPiCarX

    Load the project Git environment in every new Bash session:

    source xWalk-git-env.sh

    Show the configured Gerrit endpoint, repository, branch, CI location, and submodules:

    xwalk_git_env_show

    Show the available project Git helper commands:

    xwalk_git_env_help

    Configure identity¶

    Inspect the effective identity:

    git config user.name

    git config user.email

    Configure the identity for the current repository when it is missing:

    git config user.name "YOUR NAME"

    git config user.email "YOUR EMAIL"

    Use an identity registered in Gerrit. Do not store passwords, tokens, private keys, cookies, or authenticated URLs in Git configuration committed to the repository.

    Install the Gerrit commit hook¶

    Each independent repository needs Gerrit's commit-msg hook before its first commit. Enter the repository that will own the change, load the project Git environment, and install the hook into that repository's actual Git directory:

    scp -P "$GERRIT_SSH_PORT" "$GERRIT_USER@$GERRIT_HOST:hooks/commit-msg" "$(git rev-parse --git-path hooks/commit-msg)"

    chmod 0755 "$(git rev-parse --git-path hooks/commit-msg)"

    This form works in the superproject and in a submodule whose .git entry is a gitfile. The hook adds the stable Change-Id Gerrit uses to associate later patch sets with the same review.

    Clone and initialize¶

    Organization members may clone the submitted private integration mirror:

    git clone --recurse-submodules https://github.com/TARS-v00-01/xWalkPiCarAI.git MyPiCarX

    Enter the clone and load the Git environment:

    cd MyPiCarX

    source xWalk-git-env.sh

    The environment preserves GitHub as a read-only fetch source and configures normal uploads for Gerrit. Verify every remote before development:

    git remote -v

    Initialize an existing clone that does not yet have its submodules:

    git submodule sync --recursive

    git submodule update --init --recursive

    Do not use git submodule update --remote. That command can move a component beyond the exact submitted commit reviewed in the superproject.

    Inspect the complete workspace¶

    Show concise status for the superproject and every real submodule:

    xwalk_git_status

    Show the superproject status:

    git status --short --branch

    Show all pinned and checked-out submodule commits:

    git submodule status --recursive

    Show configured paths, URLs, branches, and actual gitlinks:

    xwalk_git_modules

    Show the current superproject commit:

    git log -1 --oneline --decorate

    Show the commit currently recorded for one submodule:

    git rev-parse HEAD:xWalk-rpi5-tool

    Show the commit checked out inside that submodule:

    git -C xWalk-rpi5-tool rev-parse HEAD

    The two hashes must match in a clean synchronized checkout.

    Update submitted superproject metadata and submodules¶

    Run these commands from the MyPiCarX root after an integration uplift is submitted:

    git pull --ff-only

    git submodule sync --recursive

    git submodule update --init --recursive

    Verify the result:

    git status

    git submodule status --recursive

    git pull --ff-only updates the submitted superproject metadata. git submodule sync --recursive applies reviewed .gitmodules URL changes. git submodule update --init --recursive checks out the exact commits recorded by the new gitlinks.

    Understand modified: SUBMODULE (new commits)¶

    The message below does not mean that source files are uncommitted:

    modified: xWalk-rpi5-tool (new commits)

    It means the submodule checkout is at a different commit from the gitlink recorded by the current superproject commit. This normally occurs after a local component commit and before its submitted integration uplift is pulled.

    Inspect both commits:

    git rev-parse HEAD:xWalk-rpi5-tool

    git -C xWalk-rpi5-tool rev-parse HEAD

    After the component and automatic integration reviews are submitted, run the three update commands from the previous section. To return immediately to the currently pinned commit without deleting the component branch, run:

    git submodule update --init --recursive -- xWalk-rpi5-tool

    This may leave the submodule checkout detached at the reviewed gitlink. Use it only when the local component work is already committed or otherwise safe.

    Start work in a component repository¶

    Enter the owning component. This example uses xWalk-rpi5-tool:

    cd /repo/joxjoh24/MyGitCode/MyPiCarX/xWalk-rpi5-tool

    Confirm that the component worktree is clean:

    git status --short --branch

    Fetch its submitted Gerrit branch:

    git fetch origin master

    Switch to the local component branch:

    git switch master

    Fast-forward to the submitted branch:

    git merge --ff-only origin/master

    Inspect recent history before editing:

    git log --oneline --decorate --max-count=10

    Review local changes¶

    Show changed paths:

    git status --short

    Show unstaged changes:

    git diff

    Show staged changes:

    git diff --cached

    Check whitespace errors:

    git diff --check

    Show a summary:

    git diff --stat

    Inspect one file:

    git diff -- path/to/file

    Stage and commit a component change¶

    Stage only reviewed paths:

    git add path/to/file another/path/to/file

    Confirm the exact staged change:

    git diff --cached --check

    git diff --cached

    Create a signed commit using the standard xWalk subject format:

    git commit -s -m "[xWalk-NNN][RPI5] Describe the change"

    The installed Gerrit commit-msg hook adds a stable Change-Id. Confirm the message, sign-off, and Change-Id before upload:

    git log -1 --format=full

    Upload a new Gerrit review¶

    From the owning component, upload an active review to master:

    git push origin HEAD:refs/for/master

    The project helper performs the same upload and selects the current repository:

    xwalk_gerrit_push "$PWD" master origin

    An active upload starts the owning module's Gerrit CI.

    Upload work in progress without starting normal active-review CI:

    git push origin HEAD:refs/for/master%wip

    The equivalent helper is:

    xwalk_gerrit_push_wip "$PWD" master origin

    Use Gerrit's Mark As Active action when the WIP patch set is ready. That transition triggers CI for the current patch set.

    Update an existing Gerrit change¶

    Keep the existing Change-Id. Edit the files, stage them, and amend the commit:

    git add path/to/updated-file

    git commit --amend --no-edit

    Upload again using the same review ref:

    git push origin HEAD:refs/for/master

    Gerrit creates a new patch set in the same change because the Change-Id remains unchanged. Never replace the Change-Id when updating a review.

    Rebase a Gerrit change¶

    For a conflict-free server-side rebase, open the Gerrit change and select Rebase. Gerrit creates a new patch set and reloads the review.

    If Gerrit reports a merge conflict, check out the local component and rebase onto the submitted branch:

    git fetch origin master

    git rebase origin/master

    List conflicted files:

    git status

    After resolving one or more conflicts, stage the resolved paths:

    git add path/to/resolved-file

    Continue the rebase:

    git rebase --continue

    Abort the rebase and return to the pre-rebase state when the conflict must be reconsidered:

    git rebase --abort

    After a successful local rebase, verify that the original Change-Id remains in the commit and upload the new patch set:

    git log -1 --format=full

    git push origin HEAD:refs/for/master

    Do not use git push --force. Gerrit patch-set upload does not require it.

    Fetch a Gerrit patch set for inspection¶

    Use the exact fetch command from the change's Download menu. A patch-set ref has this form:

    refs/changes/NN/CHANGE_NUMBER/PATCH_SET

    Fetch the selected ref through the component's Gerrit remote:

    git fetch origin refs/changes/NN/CHANGE_NUMBER/PATCH_SET

    Inspect it without moving the component branch:

    git switch --detach FETCH_HEAD

    Return to the component branch:

    git switch master

    After Gerrit Submit¶

    Confirm the component's submitted branch contains the reviewed commit:

    git fetch origin master

    git log -1 --oneline origin/master

    Do not manually commit the component pointer in xWalkPiCarAI while an automatic integration uplift is pending. Wait for the uplift review to pass complete integration CI, receive approval, and be submitted. Then update the root checkout:

    cd /repo/joxjoh24/MyGitCode/MyPiCarX

    git pull --ff-only

    git submodule sync --recursive

    git submodule update --init --recursive

    Safe staging and recovery commands¶

    Remove a path from the staging area without discarding its working-tree edit:

    git restore --staged path/to/file

    Temporarily save tracked and untracked local work only when the owner intends to restore it later:

    git stash push --include-untracked -m "temporary xWalk work"

    List saved work:

    git stash list

    Restore the latest saved work and retain the stash if conflicts occur:

    git stash apply

    Remove that stash only after verifying the restored work:

    git stash drop

    Abort an unfinished merge:

    git merge --abort

    Abort an unfinished cherry-pick:

    git cherry-pick --abort

    Never discard someone else's work. Do not use git reset --hard, destructive clean commands, force pushes, or branch deletion as routine recovery actions.

    Remote and publication checks¶

    Show fetch and push destinations:

    git remote -v

    Confirm that the GitHub remote cannot accept direct pushes:

    git remote get-url --push github

    The expected push URL is the local no-push guard:

    xwalk-gerrit-uplift-only://direct-github-push-disabled

    Compare the local branch with its configured Gerrit upstream:

    git status --short --branch

    Show local commits not yet present in the upstream branch:

    git log --oneline @{upstream}..HEAD

    Show submitted upstream commits not yet present locally:

    git log --oneline HEAD..@{upstream}

    Final clean-check sequence¶

    Run from the superproject root after submitted metadata and submodules are updated:

    git status --short --branch

    git submodule status --recursive

    xwalk_git_status

    A clean result has no modified paths, and every submodule status line begins with a space. A leading + means the checked-out component differs from the recorded gitlink, - means the submodule is uninitialized, and U means a gitlink merge conflict must be resolved.

    Commands prohibited by project policy¶

    Do not use these publication patterns:

    git push github ...
git push --force ...
git push --mirror ...
git submodule update --remote

    Development changes go to refs/for/master in Gerrit. GitHub receives only submitted branches through the configured synchronization service.
