    TARS-v00-01 submit-gated mirrors¶

    Purpose¶

    https://github.com/TARS-v00-01 contains private, submitted-code mirrors of the xWalk Gerrit repositories. Gerrit remains the only development, review, and Submit system. GitHub is not a second writable source of truth, and GitHub pull requests are not the official review workflow.

    Developer -> Gerrit review -> CI -> Code-Review +2 -> Submit -> replication -> TARS-v00-01 mirror

    Pending patch sets and refs/changes/*, refs/drafts/*, refs/cache-automerge/*, refs/meta/*, refs/users/*, refs/edit/*, and refs/starred-changes/* are not replication destinations.

    Repository mapping¶

    The machine-readable mapping is xWalk-rpi5-tool/py-agent/gerrit-tool/config/tars-mirror-map.tsv.

    Gerrit project GitHub mirror
    xWalkPiCarAI TARS-v00-01/xWalkPiCarAI
    devloper-note TARS-v00-01/devloper-note
    xWalk-rpi5 TARS-v00-01/xWalk-rpi5
    xWalk-rpi5-iw TARS-v00-01/xWalk-rpi5-iw
    xWalk-rpi5-tool TARS-v00-01/xWalk-rpi5-tool
    xWalkAgent TARS-v00-01/xWalkAgent
    xWalkAudioResources TARS-v00-01/xWalkAudioResources
    xWalkController TARS-v00-01/xWalkController
    xWalkHal TARS-v00-01/xWalkHal
    xWalkLibrary TARS-v00-01/xWalkLibrary
    xWalk-rpi5-trace TARS-v00-01/xWalk-rpi5-trace
    xWalkScheduler TARS-v00-01/xWalkScheduler
    xWalkIW TARS-v00-01/xWalkIW
    xWalk-rpi5-server TARS-v00-01/xWalk-rpi5-server

    xWalkIW retains legacy submitted history. New active interface and tooling changes use xWalk-rpi5-iw and xWalk-rpi5-tool. xWalk-rpi5-server is reserved for the gRPC server and transport adapters. It cannot become a superproject gitlink until its first implementation commit is reviewed and submitted in Gerrit.

    Clone and update¶

    Organization members clone the exact submitted integration tree with:

    git clone --recurse-submodules https://github.com/TARS-v00-01/xWalkPiCarAI.git

    Repair or initialize an existing clone with:

    git submodule sync --recursive
git submodule update --init --recursive

    The superproject uses organization-relative URLs. The exceptional Gerrit The Gerrit project and canonical GitHub repository both use devloper-note. Gerrit CI resolves its private checkout through the controlled helper.

    Developer workflow¶

    Source the repository environment, change the owning component, run its host checks, and upload only to Gerrit:

    source xWalk-git-env.sh
cd xWalk-rpi5-hw/xWalkHal
git switch master
git pull --ff-only origin master
git add <files>
git commit -s
git push origin HEAD:refs/for/master

    origin is Gerrit. The optional github remote is fetch-only and has a non-routable push URL. Do not replace origin with GitHub, push a component branch to GitHub, or open a GitHub pull request as an alternate review.

    After component Submit, update only its exact gitlink in xWalkPiCarAI. Run the complete integration checks and upload that pointer change for a separate Gerrit review and Submit.

    Replication installation¶

    Use the replication plugin version matching Gerrit's API version. Gerrit 3.14.2 includes the compatible plugin inside its WAR. Install that exact JAR, then configure one explicit remote section per mapping. Do not use an uncontrolled project wildcard.

    Each remote has these constraints:

    • one exact Gerrit project;
    • one exact private TARS-v00-01 repository;
    • only refs/heads/master:refs/heads/master;
    • no force marker in the refspec;
    • createMissingRepositories = false;
    • a repository-scoped deploy key; and
    • pinned GitHub host keys with strict checking.

    The tracked examples are:

    • xWalk-rpi5-tool/py-agent/gerrit-tool/config/tars-replication.config.example;
    • xWalk-rpi5-tool/py-agent/gerrit-tool/config/tars-ssh.config.example; and
    • xWalk-rpi5-tool/py-agent/gerrit-tool/config/tars-mirror-map.tsv.

    Reload after a configuration-only change:

    ssh -p 29419 ADMIN@GERRIT_HOST gerrit plugin reload replication

    Run an explicit idempotent verification pass with:

    ssh -p 29419 ADMIN@GERRIT_HOST replication start --all --now --wait

    Credential rotation¶

    Use one deploy key per GitHub repository. A private key is stored only in the Gerrit service account's mode-0600 SSH directory. Its public key is added to the matching GitHub repository with write permission.

    Rotate a key without interrupting submitted-code replication:

    1. Generate a new repository-specific key outside every Git checkout.
    2. Add the new public key to the matching private GitHub repository.
    3. Add a temporary SSH alias that selects the new private key.
    4. Test authentication and an idempotent replication pass.
    5. Update the remote URL to the new alias and reload the plugin.
    6. Verify the Gerrit and GitHub master hashes are identical.
    7. remove the old deploy key from GitHub and securely retire its private key.

    Never print, commit, copy into CI logs, or share a private key. Never replace a repository-scoped credential with an owner's personal token.

    GitHub Actions access¶

    Private sibling submodules require a read-only credential. Store a fine-grained machine-account token as the organization or repository secret TARS_SUBMODULE_TOKEN. Limit it to repository contents read access for the mapped repositories. The checkout helper removes the temporary Git authorization header after recursive initialization.

    Prefer a GitHub App installation token when the organization has an approved App. Do not use an owner's broad personal token.

    Developer-note artifact¶

    The xWalkPiCarAI GitHub workflow builds developer documentation only after the exact submitted integration commit has reached the private GitHub mirror. It runs xWalk-rpi5-tool/doc-tool/wiki.sh verify and uploads the generated build-devloper-note-wiki/github-site directory as a private Actions artifact. The artifact name contains the run ID and attempt number, is retained for 30 days, and is visible only to accounts authorized for the private repository.

    This workflow is a post-replication verification and distribution step. It does not upload a Gerrit patch set, replicate a branch, publish a Pages site, or push any repository ref. Gerrit remains the source of the submitted commit and its review record. The GitHub workflow run identifies the mirrored commit that produced the artifact.

    The current organization plan does not support GitHub Pages for the private integration repository. GitHub returns 404 when actions/configure-pages queries an unconfigured Pages site and returns a plan-related 422 when an administrator attempts to create it. Keep the repository private. Do not add pages: write, id-token: write, actions/configure-pages, actions/upload-pages-artifact, or actions/deploy-pages merely to suppress the error.

    Enabling Pages later requires all of the following:

    1. an organization plan that supports Pages for this private repository;
    2. an approved privacy review of the rendered documentation and component links;
    3. Pages configured with Source: GitHub Actions by an authorized administrator; and
    4. a reviewed and submitted Gerrit change that restores the least-privilege workflow permissions and deployment.

    Until then, organization members retrieve documentation from the matching private Actions run. Public users receive neither the artifact nor private component source.

    Optional global organization wiki¶

    GitHub reserves https://tars-v00-01.github.io/ for an organization site published from a repository named exactly TARS-v00-01/tars-v00-01.github.io. With the current plan, that repository must be public. GitHub does not provide private access control for an organization site. The repository, rendered site, downloaded assets, search index, sitemap, and embedded metadata must therefore be reviewed as public content. This global site is an optional future publication target and is not part of the current mirror mapping.

    Do not publish the private developer-note artifact directly to the global site. If public documentation is approved, create a distinct Gerrit project containing only the sanitized documentation source and map that one project explicitly to TARS-v00-01/tars-v00-01.github.io. Before creating either repository, approve its canonical name, visibility, content policy, responsible team, and rollback owner.

    The public documentation review must reject:

    • credentials, tokens, keys, authentication headers, and protected configuration values;
    • private Gerrit, CI, GitHub, or infrastructure addresses;
    • private source files, generated source archives, or component repository contents;
    • internal-only architecture, deployment, incident, account, and recovery details;
    • links that disclose inaccessible private paths or query parameters; and
    • unreviewed Git commit identifiers or component metadata not approved for public release.

    The only permitted publication path is:

    sanitized docs -> Gerrit patch set -> documentation CI -> review -> Submit -> exact GitHub mirror -> Pages deploy

    Pending patch sets must not reach GitHub. GitHub Actions may deploy the exact mirrored submitted revision but must not commit, push, rewrite history, or accept pull requests as the official review path. Gerrit must receive separate change-log rows for mirror status and Pages deployment status, including the GitHub commit and deployment links. The documentation CI result is reused for both publication records; creating two targets must not execute the same quality graph twice.

    If private browser access is required, do not use an organization site. Continue using private Actions artifacts, host the wiki behind authenticated college infrastructure, or obtain GitHub Enterprise Cloud approval for a private project Pages site. A private project site uses a GitHub-assigned URL and is not the global organization root.

    Validation and troubleshooting¶

    Run local structure checks with:

    xWalk-rpi5-tool/shell-agent/gerrit-tool/validate-tars-mirrors.sh

    With authenticated private-repository access, also verify every pinned commit and excluded review ref:

    xWalk-rpi5-tool/shell-agent/gerrit-tool/validate-tars-mirrors.sh --remote

    If replication fails:

    1. confirm the Gerrit plugin is enabled and API-compatible;
    2. validate replication.config with git config --file;
    3. confirm the project has one exact remote section and master-only refspec;
    4. test the remote's SSH alias with BatchMode=yes;
    5. confirm the deploy key belongs only to the matching repository;
    6. verify GitHub host keys are pinned;
    7. inspect Gerrit's replication log without printing credentials; and
    8. retry the exact project with replication start PROJECT --now --wait.

    A rejected non-fast-forward indicates divergence. Stop and investigate; never force-push either side.

    Repository rules and current limitation¶

    All repositories are private. xwalk-admins has administrative access; xwalk-developers and xwalk-readers are read-only. Repository descriptions identify the Gerrit authority and submit-gated mirror role.

    Private-repository rulesets and protected-branch enforcement require a GitHub plan that supports those features. Until that plan is available, organization team permissions and repository-scoped deploy keys reduce access, but an organization owner still has administrative push capability. Owners must not use that capability for normal development.

    After upgrading the plan, create an active default-branch ruleset that:

    • restricts updates and deletions;
    • blocks non-fast-forward pushes;
    • grants bypass only to repository deploy keys or the approved GitHub App; and
    • grants no ordinary human or pull-request merge bypass.

    Rollback¶

    Before a Gerrit Submit, abandon or revise the pending change. GitHub is unchanged because review refs are not replicated.

    After Submit, create and submit a normal Gerrit revert. Replication then fast-forwards the revert commit to GitHub. Never reset, delete, or force-push a published mirror branch.

    To suspend replication without rewriting history:

    1. disable the affected remote section or the plugin;
    2. reload the plugin;
    3. preserve queued-event and replication logs;
    4. repair credentials or mapping;
    5. compare Gerrit and GitHub branch hashes; and
    6. resume with an idempotent exact-project replication pass.
